# Итоги недели для тренера

Дата: 2026-10-16. Релиз: `release/2026-11-polish`. Без фича-флага.

## Зачем

Тренер узнаёт о клиентах по частям: «Тренировка выполнена», сигналы риска, метки в списке `/coach`. Целостной картины «как прошла неделя» нет — при 10–20 клиентах приходится обходить карточки. Итоги недели — раз в неделю один обзор всех клиентов: хорошее и плохое, кому уделить внимание.

Отличие от сигналов: сигналы — тревоги в течение недели, итоги — спокойный еженедельный обзор.

## Решения (согласовано)

- Отдельная страница со **снимком недели в БД** и историей (как «Итоги недели» пользователя, `lib/recap`), а не блок на лету.
- В строке клиента — план и тренировки, рекорды и прогрессия, программа и сигналы, тренировки без ответа тренера.
- Уведомление `COACH` с push в понедельник с 09:00 по поясу тренера; переключатель в `/settings`.
- Строки клиентов — отдельная таблица (каскад при удалении клиента), не JSON тренера.
- Без фича-флага: только чтение и одно уведомление в неделю.

## Состав и правила

**Неделя** — пн…вс; ключ — дата понедельника в поясе тренера (`recapWeekFor`). Данные клиента — за те же даты в поясе клиента (как `getClientWeekPlan`).

**Клиенты в сводке** — связь с тренером активна хотя бы часть недели и не разорвана на момент снимка; подключившиеся в течение недели — с пометкой «новый».

**Строка клиента:**

| Поле | Источник | Правило |
|---|---|---|
| План N/M | `getCalendar`, вхождения с `coachId` тренера | как «план N/M» в списке; нет назначений — нет поля |
| Тренировки | завершённые по `finishedAt` в неделе | все (и самостоятельные) и ± к прошлой неделе (считается на лету при снимке) |
| Рекорды | `XpEvent WORKOUT_COMPLETED.meta.records` | число и до 3 названий |
| Прогрессия | `meta.progression`, `kind` `up`/`deload`, без `progressionSource = own` | «Жим +5 кг», «Присед — разгрузка»; до 3, остальное «ещё N» |
| Программа | активное назначение тренера на воскресенье недели | «Нед. 5/8», «следующая — разгрузка», «заканчивается» (последние 7 дней) |
| Сигналы | открытые `CoachSignal` пары на момент снимка | типы, как в списке `/coach` |
| Без ответа | завершённые тренировки недели без комментария этого тренера | число; комментарий к упражнению — тоже ответ |

**Общие цифры:** тренировались X из Y; выполнено назначенного (сумма N/M, %) с ± к прошлому снимку; тренировки, рекорды, повышения веса; «требуют внимания» (клиентов с сигналами); «без ответа» (сумма).

**Порядок строк:** с сигналами (больше — выше) → без тренировок → с рекордами или повышениями → остальные по имени.

**Не входит:** боль и самочувствие (на сервере их нет), веса подходов и объём — детали в карточке клиента.

**Пустая неделя:** нет клиентов — снимка и уведомления нет; клиенты есть, никто не тренировался — снимок создаётся.

## Модель данных

```prisma
/// Итоги недели тренера: общие цифры (без персональных данных клиентов).
model CoachWeeklyRecap {
  id        String    @id @default(cuid())
  coachId   String
  week      String              // понедельник "YYYY-MM-DD" в поясе тренера
  data      Json                // CoachRecapTotals с version
  createdAt DateTime  @default(now())
  pushedAt  DateTime?           // push отправлен
  seenAt    DateTime?           // тренер открыл
  coach   User @relation(onDelete: Cascade)
  clients CoachRecapClient[]
  @@unique([coachId, week])
}

/// Строка клиента в итогах недели тренера.
model CoachRecapClient {
  recapId  String
  clientId String
  data     Json                 // CoachRecapRow с version
  recap  CoachWeeklyRecap @relation(onDelete: Cascade)
  client User             @relation(onDelete: Cascade)
  @@id([recapId, clientId])
  @@index([clientId])
}

// User: + notifyCoachRecap Boolean @default(true)
```

Имя и аватар клиента в JSON не хранятся — берутся из `User` при показе.

## Страница

- `/coach/recap` — последняя прошедшая неделя; `/coach/recap/<понедельник>` — конкретная; `/coach/recap/all` — список недель (по 20). Без режима тренера — 404.
- Шапка «Неделя клиентов · 13–19 окт.», «← прошлая / следующая →» по существующим снимкам.
- Плитки общих цифр (сетка 2×N на мобильном); «Требуют внимания» и «Без ответа» выделены, если не 0.
- Карточка клиента: имя (→ карточка клиента), метки сигналов (→ «Обзор»), «План 3/4 · 4 тренировки (+1) · Нед. 5/8», строки «🏆 Рекорды: …», «↑ Жим +5 кг · ↓ Тяга — разгрузка», «💬 2 тренировки без ответа» (→ вкладка «Тренировки»).
- На `/coach` — анонс «Итоги недели готовы» с 2–3 цифрами с понедельника до просмотра (`seenAt`); дальше — ссылка «Итоги недели» рядом с «Программы».
- Снимок не меняется: тренировка, дописанная задним числом после создания, в него не попадает.

## Тик и уведомления

- `processCoachRecaps(now)` в `runNotificationTick`: тренеры (`isCoach`) с клиентами в понедельник ≥ 09:00 своего пояса (`isMondayAfter`) без снимка прошлой недели; бюджет ~2 с на тик, тренеры без снимка — первыми.
- Перед снимком — пересчёт сигналов этого тренера (та же логика, что `processCoachSignals`), чтобы метки были свежими (тик сигналов — с 10:00).
- Страница до тика (с пн 00:00) создаёт снимок сразу — только последней прошедшей недели; прошлые задним числом не строятся.
- Гонка тика и страницы — `@@unique` + P2002 игнорируется.
- Push — только из тика, в понедельник, после снимка, если `pushedAt` и `seenAt` пусты и `notifyCoachRecap`; тип `COACH`, ссылка `/coach/recap/<неделя>`. Текст — чистая `recapPushBody`:
  - «Неделя клиентов: 12 из 15 тренировались, план 85%. 2 требуют внимания»;
  - без сигналов — «… 9 рекордов» (нет рекордов — без хвоста);
  - никто не тренировался — «Неделя клиентов: никто не тренировался — загляните, кому написать».
- `notifyCoachRecap = false` — нет push и колокольчика; снимок и страница работают.
- Цель Метрики `coach_recap_open` — при первом открытии (`seenAt`).

## 152-ФЗ, аккаунт

- Удаление клиента — каскад строк; общие цифры тренера остаются (обезличенные суммы).
- Удаление тренера — каскад снимков и строк.
- Разрыв связи (любой стороной, в т.ч. переход к другому тренеру) — `dropAssignments` удаляет строки клиента из всех снимков тренера.
- «Мои данные»: тренеру — `coachRecaps` (недели, общие цифры, строки с ником клиента); клиенту — `coachRecapsAboutMe` (неделя, ник тренера, строка). Проверка — `e2e/account-data.spec.ts`.
- `/privacy`: «раз в неделю тренер получает сводку по своим клиентам; при разрыве связи данные клиента из неё удаляются».
- Миграция — только новые таблицы и поле; частичные индексы `CoachLink_active_client`, `CoachComment_workout_general`, `CoachSignal_open` не трогать.

## Тесты

- Unit `lib/coach/recap.test.ts`: план N/M и его отсутствие; ± тренировок; рекорды и прогрессия (обрезка до 3, «ещё N», `own` не считается); программа (неделя, разгрузка, «заканчивается»); «без ответа» (комментарий к упражнению — ответ); порядок строк; общие цифры, % и ± (без прошлого снимка — без ±); три варианта push; граница недели в поясе.
- e2e `e2e/coach-recap.spec.ts` (два контекста — `--workers=8`; прошлые недели в БД, тик — `runTick(request, now)`):
  1. тренер + два клиента (выполнение, рекорд, прогрессия / пропуски, сигнал): тик в пн 09:xx — снимок и одно уведомление, повторный тик без дубля; страница — цифры, порядок, переходы; анонс на `/coach` пропадает после просмотра;
  2. страница до тика создаёт снимок; тик после просмотра push не шлёт;
  3. разрыв связи — строки клиента нет, общие цифры остаются;
  4. переключатель выключен — снимок есть, уведомления нет;
  5. мобильный — без горизонтальной прокрутки.
- `account-data.spec.ts`: экспорт обеих сторон, удаление клиента.

## Не в этом цикле

Email-рассылка; выбор дня и часа; сводка по группе клиентов; заметки тренера к неделе.
