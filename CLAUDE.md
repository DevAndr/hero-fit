## Идея проекта
Я хочу написать приложение для ведение тренировок. Но это будет в игровом стиле.
С каждой проведенной тренировкой повышается уровень пользователя. 
Система ачивок. Уведомления.

### Упражнения
Пользотель должен иметь возможность добавлять редактировать и удалять упражнения
У каждого упраженения будут категории. На какую группу мышц они распространяются

### Тренировки
Перед тем как начать тренировку пользователья набирает перечень упражнений, которые он хочет выполнить за свой тренировочный день.
в упражнении указывается вес и кол-во повторений
и так несколько подходов, колличество подходов неогрниченно и можно его добавлять без ограничений.

Также после выбора набора упраженений пользователь должен запусти тренировку. И тем самым расчитывать сколько времени ушло на тренировку после завершении тренировки.

Также должен быть еще таймер динамически настраиваемый кторый можно заапускать после подхода

#### Таймер отдыха
- Между подходами (динамический, задаётся в упражнении).
- Обратный отсчёт с уведомлением (звук + вибрация + push).
- Работа в фоне / при заблокированном экране → Web Workers + Notification API или Service Worker.
- Возможность +15 сек / -15 сек / пропустить.

#### Шаблоны тренировок и переиспользование уже прошедших тренировок
Пользователь не должен каждый раз собирать тренировку с нуля.
«Моя тренировка на грудь» → сохранить как шаблон.
Запуск шаблона в один клик.
Добавить недостающие упражнения в выбранный шаблон, его можно также сохранить
Готовые программы (Push/Pull/Legs, Full Body, 5×5).

#### Группы мышц — детализация
Будет основная группа категорий мышц:
Грудь, ноги, плечи, предплечья, икры, трицепс, бицепс, спина, трапеция, пресс

#### Прогрессия и рекомендации
Личный рекорд (PR) по каждому упражнению — отдельно 1RM, макс. вес, макс. повторы.
Подсказка «Пора увеличить вес» — если N тренировок подряд делаешь одинаково.
График прогресса по каждому упражнению (вес × время).
1RM калькулятор (формула Эпли: 1RM = вес × (1 + повторы/30)).

#### Streak (режим «в ударе») — механика
Серия — **недели подряд с 3+ тренировками** (`STREAK_WEEK_TARGET`). Неделя — пн 00:00 … вс 24:00 в `User.timeZone`, ключ — дата понедельника (`User.lastStreakWeek`). Неделя засчитывается сразу на 3-й тренировке (`applyWeekCredit` при завершении); пропущенные недели между засчитанными закрываются заморозками, иначе серия = 1; текущая неделя пропуском не считается, пока не кончилась. Тренировка задним числом (офлайн) не пересчитывает прошлые недели. Логика — чистые функции `lib/progress/weekly-streak.ts`, БД — `lib/progress/streak-db.ts` (`countWeekWorkouts`, `recomputeStreak`), тексты — `lib/progress/streak-copy.ts`. Счётчик недели для шапки — `User.weekWorkouts`/`weekWorkoutsKey`.
Заморозки: плановая раз в 4 недели (пока < 2) + `freezeReward` у ачивок (`streakw:4`+, вход 30+), копятся до 3; использованные — `StreakCoverWeek(FREEZE)` (из них — ачивка «Второе дыхание»).
Восстановление streak за награду: `restoreOffer` — серия ≥ 2 недель, только в неделю сгорания (`lastStreakWeek + заморозки + 2`) до четверга 00:00, цена `min(500, 50 + 50·серия)` XP только из прогресса текущего уровня (уровень не падает), раз до следующей засчитанной недели (`streakRestoredAt`); выкуп ставит `lastStreakWeek` на прошлую неделю и пишет `StreakCoverWeek(RESTORE)`; `restoreStreakAction`, кнопка на дашборде.
Уведомление «Не потеряй streak!» — когда тренировок не хватает на оставшиеся дни недели, с 12:00 по местному времени, раз в день (`User.streakReminderDay`, `shouldRemindStreak` в `lib/notifications/reminders.ts`).
Пересчёт серий по истории — `npm run db:migrate-streak` (после перехода с дневного streak; без него серии начнутся с нуля).

### Ветки и релизы
Работа идёт релизами — так экономятся минуты CI и фичи проверяются вместе до прода:
Репозиторий — свой GitLab (`origin` = `http://localhost:8929/root/hero-fit.git`), GitHub (`github`) — прежний, только для чтения истории; PR в тексте ниже = merge request (MR) в GitLab, CLI `gh`/`glab` нет — MR открываются в веб-интерфейсе.
- Релиз — ветка `release/<название>` от `main` (например, `release/2026-10-raids`). Её можно пушить в GitLab как резервную копию: без PR CI не запускается.
- Фича — ветка `feat/…` (или `fix/…`) **от релизной ветки**, не от `main`. Готова (тесты, ревью) — вливается в релизную ветку локально с `--no-ff` (одна фича — один merge-коммит), ветка фичи удаляется. Отдельных PR у фич нет.
- Релиз набран (3–5 фич или 1–2 недели — дольше не копить): поднять версию `npm version minor --no-git-tag-version` (SemVer, без git-тегов), запись о релизе с той же `version` в `lib/changelog/releases.ts` («Что нового»: человеческим языком, пункты фич под флагом — с `flag`), на релизной ветке полный локальный прогон (`npm run typecheck && npm run lint && npm test && npm run build && npm run test:e2e -- --workers=8`), затем PR `release/…` → `main`; в описании — список фич со ссылками на спеки и результаты прогона. Слияние в `main` гоняет быстрые проверки (typecheck, lint, unit) и деплоит — e2e на CI не идёт; релизная ветка удаляется.
- Срочная правка — `hotfix/…` от `main` (версия — `npm version patch --no-git-tag-version` + запись в «Что нового») → сразу PR; после слияния `main` вливается в текущую релизную ветку.
- Сломанная фича не держит релиз: `git revert -m 1 <merge-коммит фичи>` в релизной ветке.
- Миграции всех фич релиза идут по одной линии — в дев-базе не бывает миграций соседних веток.

### Разработка

- `npm run db:up` — PostgreSQL в Docker (docker-compose.yml), затем `npm run db:migrate` и `npm run db:seed`
- `.env` создаётся из `.env.example` (секреты JWT генерируются командой из комментария)
- Prisma 7: генератор `prisma-client`, клиент в `generated/prisma` (gitignored, импорт из `@/generated/prisma/client`), подключение через `@prisma/adapter-pg`, конфиг CLI в `prisma.config.ts`
- Клиент БД — `lib/db.ts`, валидированные env — `lib/env.ts` (только сервер)
- Встроенные упражнения и готовые программы имеют `userId = null` (сид `prisma/seed.ts`, идемпотентный)
- Тестовые учётки из сида (кроме `NODE_ENV=production`): `demo` / `Demo1234` (друзья, тренер, клубы, цели, итоги недели — подробности в `docs/features/platform.md`)
- UI: shadcn/ui (стиль base-nova на Base UI). Тема — `next-themes` (`components/app/theme-provider.tsx`): светлая/тёмная/системная, по умолчанию тёмная, выбор в `/settings`, хранится в localStorage. Цвета — только семантические токены из `app/globals.css` (фирменные `primary`/`chart-*`/`xp`/`streak` заданы для обеих тем). Ссылка, оформленная кнопкой — `<Link className={buttonVariants()}>` (не `Button render={<Link/>}`: Base UI вешает `role="button"` на ссылку)
- Next.js 16: перед кодом сверяться с `node_modules/next/dist/docs/`; middleware называется `proxy.ts`
- Зависимости: npm на Windows не пишет в `package-lock.json` часть необязательных wasm-зависимостей (`@emnapi/*`), и `npm ci` на Linux CI падает «Missing … from lock file». После изменения зависимостей перестроить lock в Linux: `docker run --rm -v "$PWD:/app" -w /app node:24 npm install --package-lock-only --ignore-scripts`
- Деплой — `deploy/` (инструкция — `deploy/README.md`), задача `deploy` в `.gitlab-ci.yml`; подробности — `docs/features/platform.md`
- CI — `.gitlab-ci.yml` (прежний `.github/workflows/ci.yml` — аналог для GitHub), экономит минуты: запуск только на MR и на пуш в `main` (правки одних `docs/**` и `*.md` CI не запускают), плюс вручную. Job `checks` (typecheck, lint, unit) — на каждый запуск; job `e2e` (Postgres-сервис, сборка, Playwright только desktop; 2 воркера, лимит 60 мин; VAPID-ключи генерируются на лету, секреты JWT — CI-заглушки, трейсы падений — артефакт; кэш `.next/cache` и браузера Playwright) — только вручную (Run workflow): бесплатных минут Actions на него не хватает. Поэтому полный e2e (desktop + mobile) перед PR гоняется только локально (`npm run build && npm run test:e2e -- --workers=8`) и результат пишется в описание PR
- Проверки: `npm run typecheck` (сначала `next typegen` — типы маршрутов), `npm run lint`, `npm test` (Vitest, `*.test.ts` рядом с кодом), `npm run build && npm run test:e2e` (Playwright, `e2e/`, desktop + mobile)
- Приватные страницы — в группе `app/(app)/` (layout с `AppShell` и `requireUser()`), формы входа — в `app/(auth)/`
- Уровень считается из `User.xp` функцией `levelProgress` (`lib/progress/level.ts`): переход L→L+1 стоит 100·L^1.3 XP
- Удаление своих упражнений — мягкое (`archivedAt`); встроенные (`userId = null`) не редактируются
- Авторизация (`lib/auth/*`): access JWT (15 мин) и refresh JWT (30 дн) — оба в httpOnly cookie `hf_at`/`hf_rt` (решение: Server Components должны видеть сессию). Refresh ротируется в `proxy.ts`; повтор старого refresh в течение 30 с — гонка (выдаём только access), позже — кража → сессия отзывается. Защищённые страницы/actions вызывают `requireUser()` из `lib/auth/dal.ts` (проверяет `Session.revokedAt` в БД = blacklist)
- Публичные страницы перечислены в `proxy.ts` (`PUBLIC_PAGES`), всё остальное требует входа (файлы без расширения — `PUBLIC_PREFIXES`: PWA-иконки, `/opengraph-image`)
- Версия приложения — `version` в `package.json` (SemVer: релиз — minor, hotfix — patch); unit-тест `RELEASES` требует, чтобы у первой записи была та же версия и версии росли (`compareVersions`, `lib/changelog/version.ts`). В сборку — `next.config.ts` → `process.env.APP_VERSION` и `GIT_SHA` (build arg, в CI — `$CI_COMMIT_SHORT_SHA`, локально — `dev`); показ — строка «Hero Fit v… · sha» внизу `/settings` (`buildLabel`) и значок «v…» у релиза в `/whats-new` и `/changelog`
- XP за тренировку: 50 + 5·подходы + повторы/5 + объём/200 (макс. 600) + 25 за каждый побитый PR (`lib/progress/xp.ts`); первый результат в упражнении — PR без бонуса
- e2e идут с `reducedMotion: "reduce"` (`playwright.config.ts`), анимации проверяет `e2e/animations.spec.ts` с включённым движением
- Пояс e2e — не Москва, а фиксированное смещение `Etc/GMT±N`, при котором на старте прогона местное время 12:xx (`e2e/tz.ts`, выбирается раз в главном процессе — `E2E_TZ_OFFSET`, можно задать вручную): тесты опираются на «сегодня», и прогон около полуночи ломался на смене суток. Даты и время в тестах — только через `E2E_TZ`/`E2E_TZ_OFFSET`/`localAt`, не через пояс процесса Node (на CI он UTC) и не `+03:00`
- e2e работают на отдельной базе `<имя>_test` на том же Postgres (`e2e/test-db.ts`; переопределить — `E2E_DATABASE_URL`): `playwright.config.ts` при старте создаёт её, применяет миграции и сид, сервер и хелперы подключаются к ней. Поэтому dev-сервер на основной базе e2e не мешает
- e2e может готовить историю прямо в БД через `e2e/db.ts` (pg + SQL)
- В e2e друзей быстрее связывать через `makeFriends` (`e2e/db.ts`); переключатели Base UI искать по роли `switch` (у скрытого input та же подпись)
- e2e push: фейковый push-сервис `e2e/push-server.ts` (HTTPS с самоподписанным сертификатом, сервер доверяет ему через `NODE_EXTRA_CA_CERTS`). Настоящий FCM — `E2E_REAL_PUSH=1 npm run test:e2e -- push-real`

### Сквозные правила
- Новая связь с `User` или со своим `Exercise` — проверить удаление аккаунта и выгрузку «Мои данные» (`lib/account/*`, `e2e/account-data.spec.ts`)
- Частичные уникальные индексы, которых Prisma не видит (`CoachLink_active_client`, `CoachComment_workout_general`, `CoachSignal_open`), — не удалять при `prisma migrate dev`: проверять SQL новой миграции
- Новое числовое поле ввода данных тренировки — с `selectOnFocus` (`components/ui/select-on-focus.ts`)
- Рискованная фича — сразу под фича-флагом; пункт «Что нового» про неё — с `flag`; e2e с глобальным флагом — `mode: "serial"` и только desktop
- Данные о здоровье (боль) на сервер не уходят (152-ФЗ) — только `localStorage`; исключение — данные WHOOP: на сервере по отдельному согласию при подключении, удаляются при отключении (`docs/features/training.md`)
- Бесконечных CSS/JS-анимаций на каждой странице не держать; учитывать «уменьшить движение»
- Утверждения на лендинге и в FAQ держать в соответствии с реальностью
- e2e с двумя контекстами (тренер + клиент, друзья, гильдия, клуб) гонять с `--workers=8`
